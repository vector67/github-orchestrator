GitHub Orchestrator · browser design · version 3 · 28 Sep 2026

A wall of PRs, then one PR at full width

The browser version of the orchestrator, at one address, 127.0.0.1:8720. It opens on a wall of every PR. Click one and the wall goes away. The PR takes the whole screen and always opens on its Board, with Dashboard and Terminal one tab over. A sidebar you open when you need it switches PRs without going back.

What changed since version 2
  • The Board is now a faithful copy of the real review board. I took it from frontend/app and its stylesheet, the dev preview on made-up data, and two live boards (only looked at, nothing clicked): the rail's coloured left bars, group heads, three-line rows, the panel's header, thread, code, proposal, diff and actions, and the Accept and rework dialogs, with their wording. The only change from the real board is where its header goes.
  • A third tab, Terminal, is a real shell in the PR's worktree. Everything that used to open a terminal app now happens there: add -p, commit, rebase -i, g r, a free shell, and the board's "Open a session".
  • Opening a PR always lands on the Board, and so does clicking a desktop notification.
  • Your move now sits next to the PR title, large, instead of in small type at the far right.
  • "You are the detailed reviewer" is yellow text on a grey box, not red.
  • Faint text is darker, and paused and draft rows wrap like the rest instead of being squeezed onto one line. That also fixes the bug where their cells shifted one column left.
  • Two made-up PRs show the "Waiting on others" level on the wall and in the switcher, and one of them can be opened.
  • Your answers are written into the hierarchy rules and removed from the open questions.
Earlier versions, in short

Version 2: the wall as home. Clicking a PR hid the wall and showed the PR at full width with Board and Dashboard tabs, plus a PR switcher closed by default. Hierarchy rules appeared for the first time, as proposals. The Board was redrawn from memory rather than copied from the real one.

Version 1: the wall as home, and a PR "window" copied from tmux: a PR list, a dashboard column and four tabs (Notes, Claude, Threads, Branch). The board got about 700px of width in the Threads tab.

The PRs are twelve made-up ones in an invoicing app, with the roles, next actions, paused and queued counts a busy day brings, plus #71 and #58 to show "Waiting on others". On the Board, #16 and #41 follow the layout of a live board. Every title, branch, person, comment, file, CI result, timing, agent note, transcript and terminal line is made up. The styling is the board's own.

From the wall to one PR

Click any row on the wall. The wall slides out and the PR fills the frame, on the Board. Dashboard and Terminal are the other tabs. PRs at the top left opens the switcher. Picking a PR there switches to it, and the switcher slides away. Wall goes back. On #16's Board, Accept and Send back for rework open copies of the real dialogs, and Open a session takes you to the Terminal tab.

Since this version the PR view has a fourth tab, Diff on 4, the PR's diff from its merge base to head as GitHub's Files changed draws it. A draft is anchored by selecting lines there, or in the same diff on the right of the board's draft panel, where #41's excerpt stands in below. The composer's file, from line, line and side form is gone, and a draft in your review is edited where it is. The mockups do not draw the tab; the PR diff tab spec is the decision.

The Board, copied

The real board is a 312px rail and a panel in two bands. The top band is the thread with the code it points at. The bottom band is the agent's proposal with its diff. The action bar is pinned underneath. Inside a PR it already fills the screen, so full width means leaving it alone. Its header had the logo, title, Board/Queue/Manager and the theme button, and the PR bar replaces all of those. What stays is a thin strip with the board's counts, New draft and Send review.

The switcher is not a second wall

It shows one thing per PR, the verb, stepped down by level. It has no CI and no columns. It is closed by default and closes itself after you pick, so it never takes width from the board.

The Terminal tab

A real terminal (xterm.js over a pty) whose working directory is the PR's worktree. It replaces the free shell pane, the git palette's commands that need a TTY, the g r session and the board's "Open a session". Sessions are listed on its left, so a Claude session you are steering and a shell can sit side by side. Starting one from elsewhere (the palette, the Dashboard's git block, the board's button) switches you to this tab with the command already running.

tmux mode stays. So the dashboard's fields, and the verb, need one definition that both the tmux dashboard and the web dashboard render. Otherwise the two drift apart the first time someone adds a field.

The directions I compared first

A · Inbox first

One queue of decisions across all PRs. A working agent isn't an inbox item, so the dashboard and live notes would end up in a drawer. Rejected. Its ordering lives on as the wall's first group.

B · Control room tiles

Every PR as a tile at once. At 12 PRs each tile cuts off what you wanted to read, and there's no room to decide threads. Rejected. Its live line per working agent lives on in the wall's Claude column.

C · Wall, then the PR (chosen)

A dense wall as home, and one PR at a time at full width: Board, Dashboard, Terminal.

Runs

A third page beside the wall: runs.jsonl as a table (ended, PR, event, time taken, exit, cost) plus the watcher's health, so status, runs and a first look at logs don't need a terminal. Each row opens that run's transcript in its PR's Dashboard. A failed run is red; a run that went fine is plain text.

What this asks of the plumbing

One origin

Wall and every PR live at 8720. The hub proxies /pr/24/api/… to that PR's board port, so the board API stays as it is. The PR view is a route of the same Ember app, so the wall disappears without a page load, and a notification can link straight to /pr/24.

One definition, two renderers

Both the tmux dashboard and the web dashboard render the dashboard's fields and the "your move" verb. Compute them once, server-side, as data (not as terminal lines), and have render_dashboard and the web app both draw from it. The verb also folds in the board's state (fixes ready, drafts, answered threads) and frozen or paused.

A wall feed and streams

The wall needs every PR's dashboard facts, its manager's snapshot and its group in one request. Today /api/pull-requests has five fields. Notes, Claude output and the terminal want streams (server-sent events, a websocket for the pty) rather than polling. The feed should say when a PR changed group, so the page can tag it.

A pty per worktree

The Terminal tab needs a server-side pty in the worktree, carried over a websocket to xterm.js. It replaces split in browser mode. Whether sessions outlive the page is question 2.

Questions still open

  1. Draft pull requests, the ones whose next step is "mark ready for review": where do they go on the wall? This is about whole PRs still in draft on GitHub, not draft review comments. Five of your twelve PRs are like that. Here they sit in a "Drafts" group at the bottom, below Paused. They could instead be hidden until something happens on them, or count as needing you.
  2. Should Terminal tab sessions outlive the browser tab? If a session runs inside tmux (one tmux window per PR, which tmux mode already has), it survives closing the page and reloading the manager, and you can attach to it from a real terminal too. A plain pty dies with the page.
  3. Keep the board's counts strip inside the Board tab? I kept it, with New draft and Send review, because it belongs to the board. The PR header and the tab count already cover part of it.
