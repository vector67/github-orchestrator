# Next move for a pull request: plan

Carries out [the next move spec](../specs/2026-10-01-next-move-design.md). The
spec is the decision. This plan sets the order of the steps and how each one is
judged. Rule IDs (G1–G4, R, V1–V12, A1–A11) are the spec's.

## How to work

- Every change follows `.claude/skills/normal-workflow`. Load `tdd` for
  anything that changes behaviour and `refactor` for reshaping. The user has
  approved running the steps straight through without stopping to confirm.
- Each step gets its own branch in its own worktree, cut from local `main`. It
  is merged and restarted before the next step starts.
- Run `make lint-python` and `make test-python` before each commit. When the
  commit touches `frontend/`, run the full `make lint` and `make test` as well,
  and report the pass counts. A falling count fails the check unless the commit
  message names each deleted test and what made it impossible.
- **One decision.** The rules live in one private module in `pr_manager`,
  `pr_manager/_next_move.py`. It takes the facts, the thread counts and the
  manager's own state, and returns one value: the move code, the numbers and
  people the wording needs, the wall group, whether the move is muted, the
  flags and the counts. Any of these fails the step:
  - a rule written anywhere else: the front end, the terminal dashboard,
    `change_detection` or the projection;
  - a second copy of the bot list (`claude`, `codex`, `copilot`);
  - a front-end helper that reads CI, review or thread facts to choose wording
    the code doesn't already name.
- **Facts carry inputs, not conclusions.** `change_detection` hands over what
  GitHub said: draft, merge state, review decision, who is requested, each
  reviewer's last verdict, mentions. `Want`, `Blocker`, `author_wants`,
  `reviewer_wants`, `viewer_wants` and `blocker` are removed in step 1, not
  kept next to the new decision.
- **The contract carries a code, never text.** `Dashboard.move` becomes one
  object: a `Move` code, then named number and people fields, `muted`, the
  `flags` and the counts. `DashboardAction` goes. Each interface words the
  code itself: the board in `frontend/app/data/dashboard.ts`, and the tmux
  terminal dashboard in `pr_manager/_dashboard.py`. Regenerate `api.ts` and
  the contract copy through `tests/board_api/test_contract_copy.py`.
- **Budgets.** `make interface-report` must show no package with more exports
  than it has on `main` when the step starts, and no class with more methods.
  `board_api` is at 5/5, so a new export there replaces one. `change_detection`
  and `conversation` are over budget and may only shrink. Data fields on a
  dataclass are not methods.
- **Data on disk.** Snapshots, thread records and queue files written before a
  step still load. Read a missing key as its old meaning, write the new form,
  and keep the translation in one place inside the module that owns the file.
  A `ReviewRequested` queue file without the new fields still loads.
- **GitHub calls.** A new `gh` call is added to the `PullRequests` protocol,
  `github/fake.py` and `tests/github/scripted_gh.py` together, and is covered
  by `tests/github/test_contract.py` against both. Nothing a step does may
  approve, reject, reply, post, push, resolve or dismiss on a real PR.
- Tests assert behaviour and structure, never colours, borders or widths. "The
  NEXT box is grey" is tested as the muted marker on it, not as a colour.
- Code carries no comments (the user's rule).
- Check the look of any step that changes the board, in both themes, in the dev
  preview (`python -m github_orchestrator.preview`, after
  `make build_frontend`) or against the running hub. Take headless Chrome
  screenshots, look at them, and load the page with console logging on. Any
  `Uncaught` error fails the check.
- When the spec leaves a choice open, make it, record it in the decision log
  with the reason, and name it in the report.
- Bound every long command with `timeout` (a suite with `timeout 300`), so a
  hang shows up as a failure rather than silence.
- When a step finishes, mark it **Done** below with its last commit hash, in
  the same commit as its last code change.

## Steps

1. **One decision, same behaviour.** A refactor. `_your_move`, `_board_move`,
   `_wanted_of_author`, `_wanted_of_reviewer` and `_merge_blocker` collapse
   into `pr_manager/_next_move.py`. Facts lose `Want`, `Blocker` and the three
   `*_wants`, and gain the raw inputs those functions read: `draft`, the merge
   state (clean, blocked, behind, conflicts, unstable, unknown) and whether
   the viewer is requested. The contract's `move` becomes the code object
   described above. Its codes cover every move the board shows today,
   including the ones `wantedMoveOf` words, so the board, the wall and the
   terminal dashboard read the same after this step as before.
   `moveOf`, `wantedMoveOf`, `actionOf`, `detailOf` and `blockerOf` become
   wording of the code. The band's "PR state" line words the code too. The
   fixtures in `fake-board.ts` and the Python tests change shape to the new
   contract, but no assertion on what a user reads changes: the pinned frames
   and the wall's verb tests assert the same text as before. A test whose
   expected wording has to change is a behaviour change and doesn't belong in
   this step.
2. **Before anything else, and someone else's PR.** G1–G4, R, then V1 and
   V3–V11 with their wording, using the IDs as move codes where that's
   natural. "Your threads M/N answered" counts only threads the viewer opened.
   This fixes #41. "Waiting on reviewers" comes from GitHub's review
   decision, not from the requested list. This fixes #42. An empty decision
   gives "Waiting on the author · X still requested". V2 without mentions:
   a PR where you are neither author nor reviewer is off the wall. Dismissal
   (spec "Dismissing a PR"): a dismissed PR is off the wall until its next
   event, unless G1 holds. The Hidden group goes. Write a test for each of
   #41 and #42 from the spec's Problem section.
3. **Your PR.** A1–A11 and the fallback, with the Draft group placed after
   Needs you, and a muted move on a draft. Thread counts split human from bot
   by the fixed list, skip your own comments and unsent drafts, and give
   done, to decide and agent on, as the spec defines them. "Ready to merge"
   replaces "Merge the PR". The `mark-ready` control and `Want.MARK_READY`
   wording go, because there is no "Mark ready" step.
4. **Flags and the top bar.** Draft, Fix CI, Rebase and N unresolved threads
   show as flags beside NEXT, on the wall row and in the switcher whenever
   they're true. "CI failing" folds into Fix CI. The counts line shows on
   every PR: human comments M/N done and bot comments M/N done on yours, and
   your threads M/N answered on someone else's. A draft gets a grey Draft pill
   before the title, and a NEXT box marked muted, with no yellow.
5. **Mentions, back end.** A `mentions:@me` search beside the other two, run at
   most once a minute on its own clock, with the last result kept between
   searches so a skipped cycle doesn't drop a PR. A mentioned PR stays watched
   until it is merged or closed. Facts gain the mentions: who, when, and
   whether you replied after. They come from comment bodies the thread poll
   already fetches: issue comments, review comments, review bodies and the PR
   body. A reply is a comment of yours, posted after the mention, on the same
   thread, or in the PR's conversation when the mention was a top-level
   comment. Rules V2, V2b, V10 and V12, and the Mentioned group, which sits
   below On hold.
6. **The mention card.** On a PR you didn't author, a mention shows as its own
   card with one button, **Reply and resolve**. The button opens the existing
   decide dialog, posts the reply to GitHub, and resolves the mention on the
   board only. **Defer** is a link at the bottom right. There is no
   "Reply to X" link under the comment and no line for a proposal. Build on
   `resolve-here`, not on a second dialog.
7. **The review agent on every request.** A re-request (requested again after
   you submitted a review) fires `ReviewRequested` the way a first request
   does. Detect it from a stored `review_requested` flag going from an
   explicit false to true, so snapshots written before the flag existed don't
   fire. A re-request gets a re-review prompt that sets out your last review
   and what it said, every commit since (from `git log` in the worktree), and
   the threads that have been replied to. Pin it beside the existing prompts
   in `tests/agent_runs/pinned/`. "Review this PR" and "Re-review" show a
   **Start a review agent** button. It posts `/manager:start-review`, which
   queues a `ReviewRequested` the way the watcher does.

After the last step, `run-plan-steps` step 6: measure the test speed and add a
row to `docs/test-speed.md`.
